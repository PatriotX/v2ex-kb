AI 中转站向 Agent 注入窃取 SSH/apikey 的脚本

事件置信度 中有效更新 2026-10-20

置信依据：单帖亲历 + 多条回复附和

主题 安全与隐私 AI编程工具
实体 ChatGPT-Codex
标签 #中转站 #AI Agent #供应链 #凭据窃取

摘要

“中转站”指转售 OpenAI/Anthropic 等模型 API 的第三方代理服务，价格远低于官方，在国内开发者中很普遍。2026-08 一位用户在以 full access 模式通过某“公益”中转站使用 Codex 时，发现模型思维链里突然出现一段命令：遍历主机信息、环境变量、SSH 私钥、云厂商凭据、各种 token、.env、Codex 配置和 shell 历史，打包后 curl POST 到一个外部域名。中转站处在提示词与模型回复之间，可以注入系统提示词或篡改返回内容，而 Agent 拥有本机执行权限——两者叠加，就等于把家门钥匙交给了中转方。社区结论很一致：用中转站就别给 Agent 高权限、别让它无人值守；真正的解决办法是用官方订阅/官方 API，或者把凭据与 Agent 运行环境隔离。

来龙去脉

  • 2026-03-06（预警）：有人提问中转站会不会在提示词里“夹带了一些私货 比如扫描某些敏感文件(加密钱包的默认存储路径)然后上传啥的”t/1196220↗，并担心“如果是龙虾这种纯自动的机器人是不是就会中招?”t/1196220↗。
  • 2026-05-15（旁证）：数据库被删库勒索的帖子里，有人猜测“是不是 vibecoding 用的中转站把你文件扒了，密码泄露了”t/1212822 #27 ❤4↗。
  • 2026-08-10（实锤）：楼主使用某“公益站”，“开的 full access ，在写一个 glance 的自定义模块，用着用着思维链突然出现这种东西，心生警觉点了暂停”t/1233104↗，并告诫“大家用中转站的真的不能 full access+无人值守，家都给你偷了”t/1233104↗。
  • 同帖有人补充：“这个站前几天就公告说有脚本注入，窃取.codex 和.claude 目录下的配置文件里的 api key ，没想到又出现了”t/1233104 #3↗，还有人在同一域名下发现了钓鱼页面（t/1233104 #1↗）。

各方观点

① 中转站天然不可信，别用（主流）

  • “会，怕就不要用。”t/1196220 #9 ❤4↗——但被反驳“梯子信息有 TLS 保护，能一样吗”t/1196220 #12 ❤2↗，即中转站能看到明文且能改内容，风险比代理更大。
  • “中转站毫无隐私可言，不知道为啥 V2 这么注重隐私的地方还有人用中转”t/1233104 #17↗
  • “免费的是最贵的，这个道理应该深入人心。”t/1233104 #11↗；“"可是中转站便宜啊"”t/1233104 #15 ❤5↗（❤5，反讽）

② 可以用，但要降权：只写代码，不跑高权限 Agent

  • “所以不要用中转站弄一些涉及隐私的东西，写写代码之类的问题不大。跑权限很大的 agent 还是算了。”t/1196220 #10↗
  • “中转站注入的是系统提示词 优先级很高”t/1196220 #8 ❤1↗，防御手段“无非是禁止读取 env 文件或者脚本运行前确认之类的 但这种也会影响体验”t/1196220 #8 ❤1↗

③ 技术性缓解

  • “所以把 curl post 指令加到黑名单里不就可以了吗”t/1233104 #21↗（单一黑名单很容易绕过，属于不完整方案）
  • “把 OAuth / token 和 agent 的本机权限隔开，不要把一些重要的密钥什么的都放在本地”t/1233104 #41 ❤1↗
  • “自从发现龙虾可以用 codex oauth 和 claude setuptoken 之后就对中转站没有需求了”t/1196220 #16↗

④ 即便不用中转站也有类似风险

  • “openclaw 最危险的应该是提示词注入吧，这东西甚至都不需要中间人，只要访问到陷阱网页就可以直接策反 ai 了”t/1196220 #14↗
  • 有人把此事与 npm 投毒联系起来（t/1233104 #16↗，未证实二者有关，参见 npm 投毒频发，socket.dev 包一层能否解决？）。

比例：两帖合计约 70 条回复，没有人认为中转站可以放心给 full access；分歧只在“完全不用”还是“降权使用”。

实用建议 / 检查清单

  • 不要让经由中转站的 Agent 拥有 full access 或无人值守运行：这是楼主最直接的教训（t/1233104↗）。
  • 把凭据移出 Agent 能读到的范围：SSH 私钥、云凭据、.env、各类 token 都在上述收集清单里；考虑在容器/独立用户/虚拟机中运行 Agent，并把 OAuth/token 托管在 Agent 之外（t/1233104↗、t/1233104 #41 ❤1↗）。
  • 执行前确认 + 禁读敏感文件：会影响体验，但能挡住一部分注入（t/1196220 #8 ❤1↗）。
  • 出口控制：对 Agent 运行环境限制外连域名比单纯拉黑 curl 更有效（归纳；t/1233104 #21↗ 提出的黑名单思路过窄）。
  • 中招后：轮换所有可能泄露的密钥（SSH、云、API key、git/npm token），检查 shell 历史与 crontab 有无残留，并排查中转站对话中是否发送过敏感内容（t/1233104↗、t/1233104 #3↗）。
  • 优先官方渠道：官方订阅或官方 API；若因地区限制无法使用，参见 及其风险。
  • 组织视角：开发者私下使用中转站属于影子 AI 风险，公司代码和凭据可能流经第三方（见 企业安全启示：开发者普遍用共享账号、中转、代充、接码）。

未定论与局限

  • 注入发生在中转站侧还是模型输出被其他途径污染（例如项目依赖），帖内没有取证结论；楼主只报告了现象。
  • 是否真的有数据被外传，楼主“正在补救中”，后续未见更新；另一位用户“当时刚好开着抓包，没发现有被上传到迹象”t/1233104 #3↗。
  • 涉事中转站名称来自楼主描述，本卡不做进一步定性。
  • 主要证据只有一个实锤帖（41 回复），样本有限。
